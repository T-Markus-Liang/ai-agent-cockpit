Architecture Upgrade · 2026-10-06 · v1.2

Personal AI Operating System

面向 MacBook、微信、多 Agent CLI、桌面 App、GitHub、Cloud Agent 与远程设备的统一 AI 大管家设计方案。 核心目标不是“再做一个聊天机器人”，而是把个人工作环境升级成一个可路由、可验证、可审计、可扩展的 Agent Control Plane。

核心判断： 真正决定系统是否能长期自动运行的，不是某个模型有多聪明，而是 Verification、Eval、Hard Constraints、独立 Memory 与清晰的任务状态机。 Lauren Tan 的 pstack / Cursor workflow 明确强调 reusable playbooks、review processes、debugging workflows 和长期记忆式能力积累 [1][3]。

2. 核心原则

原则落地要求依据
Chief 不做重活 Chief 负责理解、规划、路由、监督、汇总；具体执行交给专职 Agent。 pstack 使用高阶 router 将任务导向不同 skill / playbook [1][3]
Harness 与模型解耦 Claude、Codex、OpenCode 都视作可替换 worker；能力由统一 Task Contract 调用。 已有 pstack 的 harness-neutral / cross-agent 移植支持 Claude Code、Codex、OpenCode、Gemini 等 [2][4]
Agent Done ≠ Done 所有任务必须进入测试、验证、review、证据采集阶段。 workshop 重点是 reusable engineering workflows 与 review / debugging process [1]
规则尽量机器化 安全、架构和质量要求优先变成脚本、CI、lint、权限 gate，而不是只写 Prompt。 pstack 的工程方式强调规则、skills、tools、playbooks [3]
记忆按角色隔离 不同 Agent / 项目分开记忆，避免一个超级上下文污染全部任务。 “Agents are like new hires in constant amnesia”，通过 rules / skills / tools / long-term memory 弥补 [3]

4. Personal Chief of Staff

Chief 的职责必须严格限制，否则它会迅速进化成一个什么都做、什么都知道一点、最后什么都管理不好的上下文沼泽。

Chief 应负责

Intent Recognition Task Planning Agent Routing Priority Resource Budget Progress Tracking Approval Summary

Chief 不应负责

长时间写代码、直接改大量文件、手工点击 GUI、自己跑全部测试、长期保存所有项目细节。

建议 Chief 的输出不是自然语言散文，而是一个标准化 Task Plan：

{
  "goal": "修复 Feedlot 仿真中动物路径穿模",
  "project": "autoware-feedlot",
  "risk_level": 1,
  "worker": "claude-code",
  "reviewer": "codex",
  "verification": [
    "build",
    "unit_test",
    "simulation_log_check"
  ],
  "requires_human_approval": false
}

5. Feature Map：给大管家一张机器地图

Agent 不应每次重新探索机器上有什么。系统要维护一个动态 Feature Map，描述软件、CLI、机器、账号、可执行能力和边界。

apps:
  claude_code:
    type: cli
    capabilities: [coding, planning, review]
  codex:
    type: cli
    capabilities: [coding, cloud_task, review]
  opencode:
    type: cli
    capabilities: [coding, cheap_execution]
  github:
    type: service
    capabilities: [issue, branch, pull_request, actions]
  chrome:
    type: gui
    capabilities: [browse, devtools, webapp]
  wechat:
    type: messenger
    capabilities: [receive, reply, approve]

machines:
  macbook:
    capabilities: [macos, build, gui, simulation]
  orin:
    capabilities: [cuda, ros2, hardware_test]
Feature Map 是把“Agent 猜环境”升级为“Agent 查能力目录”。这类结构化上下文与 pstack 的工程 playbook 思路一致：先建立可复用工作方法，再让 Agent 执行，而不是每个 session 从零摸索 [1]。

6. Model / Agent Router

不要绑定“一个万能模型”。建议按任务类型动态路由：

任务类型首选备选理由
架构设计 / 高复杂度 ReviewClaudeCodex深层代码理解与设计优先
大规模执行 / 重构Claude CodeCodex CLI需要长上下文和多文件操作
廉价批处理OpenCode / DeepSeekKimi降低 token 成本
长时云任务Claude Cloud / Devin CloudGitHub Actions释放本机和人工监督
第二意见不同模型 Reviewermulti-model panel降低同模型自证偏差

pstack 已经出现针对 Claude Code、Codex、OpenCode、Gemini 等不同 harness 的移植， 说明方法论本身可以和具体模型解耦 [2][4]。

7. Task Object 与状态机

每个任务必须是数据库中的一等对象，而不是散落在聊天历史里的几句话。

{
  "task_id": "sim-1842",
  "project": "autoware-feedlot",
  "source": "wechat",
  "intent": "fix_bug",
  "worker": "claude-code",
  "reviewer": "codex",
  "status": "VERIFYING",
  "workspace": "~/AgentWorkspace/autoware/task-1842",
  "branch": "agent/sim-1842",
  "artifacts": [],
  "evidence": [],
  "created_at": "...",
  "updated_at": "..."
}

建议状态机：

CREATED
  ↓
PLANNED
  ↓
RUNNING
  ↓
IMPLEMENTED
  ↓
VERIFYING
  ↓
REVIEWING
  ↓
READY
  ↓
MERGED / DELIVERED

失败分支：
RUNNING / VERIFYING / REVIEWING
  ↓
FAILED
  ↓
RETRY / REROUTE / HUMAN_REVIEW

8. 独立 Memory 与 Context 隔离

不要建立一个无限膨胀的“万能记忆”。建议最少拆分：

Chief Memory

用户偏好、系统拓扑、Agent 能力、长期规则。

Project Memory

代码结构、历史决策、项目约束、known issues。

Role Memory

Reviewer、Tester、Researcher 等角色自己的经验与 rubric。

Lauren Tan 公开描述 pstack 时把 Agent 类比成“高能力但持续失忆的新员工”，并强调使用 rules、skills、tools 和 long-term memory 来近似补偿这一问题 [3]。

9. Skills / Playbooks：真正可积累的资产

应把经验从 Prompt 中剥离出来，形成版本化 Skill。

Skill作用系统内对应能力
/how深入理解子系统怎么工作Research / Codebase Understanding
/why追溯源代码、历史、issue 等解释为何这样设计Decision Reconstruction
/architect先稳定类型、数据结构、边界Design Gate
/tdd先失败测试，再修复Verification-first
/interrogate多模型对抗 ReviewAdversarial Review
/arenaN 个并行方案，提取最优部分Parallel Candidate Search
/show-me-your-work保留可审计决策轨迹Evidence / Audit Trail

这些 skill 在 Lauren Tan 对 pstack 的公开介绍中被直接列出 [3]； workshop 页面也点名 /architect、/interrogate、/arena、/tdd [1]。

10. Verification Layer：系统的心脏

定义： Agent 不能通过“我已经修改了代码”证明任务完成。必须提供可复现证据。
任务最低验证要求
代码 Bugrepro → failing test → fix → passing test
Web启动应用 → 浏览器交互 → UI state / screenshot
CLI真实命令执行 → exit code → stdout/stderr
性能before / after benchmark 或 profile
仿真build → launch → log / metric → expected behavior
GitHub PRCI → review threads → merge readiness

pstack 的官方/社区说明把它定位为用于理解代码、设计修改、测试修复以及准备 PR 的严格工作流 [2]，而不是单纯代码生成工具。

11. Eval / Judge Layer：连 Skill 本身也要被测试

Agent workflow 也会退化，因此要有 Eval Harness：

Skill v1
  ↓
生成 N 个测试任务
  ↓
多个独立 Agent 执行
  ↓
Blind Judge
  ↓
Rubric Score
  ↓
Failure Analysis
  ↓
Skill v2
  ↓
Regression Eval

建议核心指标：

任务质量

  • 正确率
  • 测试通过率
  • 回归率
  • Reviewer 驳回率

系统效率

  • 人工干预次数
  • 平均重试次数
  • token / cost
  • 从接单到 READY 的时间

12. Policy / Permission Engine

权限建议五层：

等级能力默认策略
L0读文件、查状态、搜索自动
L1改项目文件、跑测试、Git branch自动
L2安装依赖、启动服务、修改开发环境自动 + 日志
L3删除、覆盖、sudo、系统设置Policy Gate / 条件审批
L4支付、生产部署、代表用户发送外部消息微信二次确认
不要只写一句“不要删除重要文件”。应在工具层直接拦截高风险命令。 任何能由程序强制执行的规则，都不应该只依赖 Prompt 和记忆。

13. Local Chief + Cloud Workers

推荐分工：

微信
  ↓
MacBook Personal Chief
  ↓
Router
  ├─ 轻量任务 → OpenCode / DeepSeek
  ├─ 复杂代码 → Claude Code / Codex
  ├─ 长时开发 → Claude Cloud
  ├─ 完整云电脑任务 → Devin Cloud
  ├─ CI / batch → GitHub Actions
  └─ 硬件任务 → SSH → Orin

重点不是“云端越多越好”，而是先让本地 workflow 可验证，再把已经稳定的任务迁移到 Cloud。

14. 微信交互层

微信只承担四类交互：

Command

“把 1842 交给 Codex 重做。”

Status

“Feedlot 昨天的问题修好了吗？”

Approval

“允许 L4：部署到生产。”

Evidence

接收摘要、截图、失败原因、PR、性能对比。

示例输出：

Feedlot 项目：3 个任务

- Claude Code 完成
- build/test 全通过
- Codex Review 通过
- PR #312

#1843 ⚠ RETRY

#1844 ⏸ WAITING_LOCAL

15. 推荐落地路线

阶段范围目标
Phase 1 微信 → Chief → 2 个 CLI Agent → Task DB 先打通“派单、状态、结果回传”闭环
Phase 2 加入 Git worktree、独立 workspace、Reviewer 支持安全并发
Phase 3 Verification + Evidence Pack 把“AI 说完成”升级成“系统证明完成”
Phase 4 Skills / Playbooks + pstack 移植 把经验做成长期资产
Phase 5 Eval / Judge / Regression 防止 skill 和 agent workflow 漂移
Phase 6 Claude Cloud / Devin Cloud / GitHub Actions 把已验证的任务迁移到云端自动执行
Phase 7 GUI / App / Orin / 其他机器 形成真正的 Personal AI OS
优先级： 第一版不要做“全自动控制整台 Mac”。先做好 Task Object、Router、Verification、Permission。 这些底座如果烂，后面 Agent 越多，只会更高效地制造混乱。

16. 最终推荐技术边界

必须长期稳定

Task DB、Policy Engine、Feature Map、Evidence Store、Router Contract、Audit Log。

应该可替换

Claude / Codex / OpenCode / Kimi / Devin / Cloud Provider / Browser Agent。

最终设计哲学：

模型 = 可替换算力
Agent = 专职员工
Skill = SOP
Verification = 质检
Eval = 培训考试
Policy = 公司制度
Task DB = 工单系统
Chief = 调度主管
微信 = 老板的遥控器

这才是长期可扩展的结构。否则所谓“AI 大管家”，最终往往只是一个权限很大的聊天机器人。 这种东西非常符合人类工程史传统：先给它 root，再祈祷它成熟。

17. 本机接入与控制面边界

当前实现状态：本轮已开始执行重构。已落地根目录兼容期控制面：Task / SessionRef / Execution / Evidence / Approval / AgentCapability 运行时契约、Codex/OpenCode/Kimi 只读会话索引、WorkBuddy/Devin/Claude Code/Antigravity 能力发现、CLI/HTTP 查询入口和控制面 launchd 定义。它仍不写入外部 Agent 历史、不读取凭据、不承担 Chief 派单；下方未标记为已实现的模块仍是路线图。

17.1 微信、Chief 与 Worker 解耦

微信是移动设备的消息、状态、审批和证据入口，不包含 Worker 选择逻辑。默认 Codex 或 Kimi 可担任 Chief，负责理解、规划、分层查阅上下文、调度和汇总；具体任务由专职 Worker 执行。切换微信桥的 ACP preset 只是更换入口 Agent，不等于 Chief 已获得跨 Agent 调度能力。

微信 / 手机网页
  ↓
Personal Chief（默认 Codex 或 Kimi，可替换）
  ↓
统一 Task / Session / Policy / Memory / Evidence 控制面
  ↓
执行适配器
  ├─ Cezar：已有工作流、worktree、run 与 review gate
  ├─ 本机 Agent：Devin CLI、Codex、Kimi 等
  └─ 云端服务：Devin Cloud、GitHub Actions 等

Cezar 是可复用的执行引擎和界面，不是全部本机 App 历史会话的唯一管理者。自有控制面通过明确适配边界接入 Cezar，不把全部业务继续塞入 gateway，也不大规模改写 vendor。

17.2 Session、Task、Execution 分开管理

对象职责与所有者
Session原生 Agent 管理对话和上下文。引用包含 Agent 来源、账号/profile 范围、原生会话 ID 与工作目录；标题不是唯一标识。
Task控制面管理用户目标、约束、依赖、验收和最终状态。任务可以关联多个执行尝试。
Execution一次派给某个 Worker 或引擎的执行。关联原生 Session、Cezar run 或云任务 ID。转派是新执行，不伪装成原生上下文无损迁移。

控制面与 Cezar 不得同时启动同一次执行。使用请求幂等标识、原生会话执行锁和事件关联避免重复派单；Cezar 保留自身 run/worktree 状态所有权，控制面接收证据和事件后决定 Task 状态。Worker 报告完成只能进入待验证状态，不能直接进入最终完成状态。

17.3 分层历史检索与恢复

会话元数据 → 摘要 → 相关消息片段 → 必要的完整上下文

外部 Agent 历史默认只读，结果保留来源和读取范围；摘要不等于完整历史，不全量复制为 Chief 的万能上下文。优先使用经验证的原生接口；无支持接口时才评估只读文件或 SQLite 适配，不写外部历史库、不读取或转交认证凭据。

恢复必须确认 Agent、profile、原生会话 ID 与工作目录。恢复失败要明确返回错误，不得静默创建新会话并声称继续成功。App 与控制面对同一会话的并发写入需要可靠协调；无法判断是否空闲时，暂停恢复并请求确认，不声称本机锁可以阻止未接入的 App 写入。

17.4 本机 Devin 与 Devin Cloud

本机 Devin CLI/App 和 Devin Cloud 是两个独立适配器，分别管理认证、会话标识、工作空间、计费及执行证据。原有 Phase 6 的云电脑场景指 Devin Cloud；本机 Devin 接入可以在本机会话与 Worker 阶段验证，但不代表云端能力已打通。

观察项当前证据与限制
Devin 本机 ACP已验证 devin acp 的 initialize 握手与 session/new 创建会话。未验证真实任务 prompt、旧会话 list/load、历史读取和完整工具调用；创建会话成功不证明模型请求的鉴权与计费路径已可用。
微信入口已检查配置与启动定义使用默认 Codex；Devin preset 已存在，但不是管家工具注册，也不代表微信已切换到 Devin。
Cezar已有任务派发、继续 run 和 ACP 实现可供接入参考；已检查的 runner 注册表没有 Devin。
本机能力展示已检查的 Local agents 页面包含静态能力声明；声明可接入不能作为真实运行健康或调度成功的证明。
统一控制面在已检查的项目入口与调度代码中尚未发现完整跨 Agent 历史检索、Chief 工具层和任务关联闭环；本节描述的是后续设计。

17.5 权限边界

第 12 节权限等级是目标策略，不是已部署授权，也不覆盖用户当前的“只更新文档”指令。连接器确认身份，Policy 对具体操作、参数、目标和有效期做确定性校验；审批不得泛化复用。既有部分 ACP runner 使用自动批准工具，协议处理可复用，但自动批准策略不能直接作为新控制面的默认值。

工作目录不等于沙箱，Agent 声明支持权限不等于实际强制隔离。无法可靠约束的操作必须报告限制并停止自动执行；不得开启 bypass、自动审批或放宽现有安全设置来绕过接入失败。Policy 在执行前生效，执行后还需验证和审计。

19. pstack / SpaceXAI 方法论的吸收

设计文档最初引用的 Lauren Tan 并不是普通的“Claude Code 工程师”：公开资料显示她参与 SpaceXAI 的 Grok Bot 与 Cursor 工作，并公开分享了 pstack——把 Agent 从一次性聊天升级为带有 playbook、验证、review、并行协作和长期记忆的工程系统。pstack 的公开仓库还记录了 Codex、Claude Code、OpenCode、Gemini CLI 等运行时的移植方式，以及在无法并行时的顺序降级路径。

Skill-first Routing

Chief 先选择工作流/Skill，再选择 worker；不要把所有任务都交给同一个“万能 Agent”。

Chief + Workers

Chief 负责理解、拆解和监督；Worker 负责执行；Reviewer 独立检查结果。复杂任务可以并行，无法并行时顺序执行。

Verification-first

把测试、运行、截图、日志、diff 和 review 作为任务状态的一部分，Agent 自报完成不能直接结案。

pstack 做法Personal AI OS 吸收方式第一阶段实现
poteto-mode / 自动路由Chief 根据意图、风险和能力目录选择 Skill 与 WorkerFeature Map + Task Contract
arena / 并行候选为互不冲突的方案创建独立 Execution 和 worktree保留 Cezar worktree，记录 parent/child Execution
interrogate / 对抗 review不同模型或不同角色独立审查，不让实现 Agent 自证Reviewer 状态和 Evidence Pack
tdd / verification skill将失败测试、修复、验证作为强制状态流VERIFYING → REVIEWING → READY
show-me-your-work保留命令、输入、输出、diff、来源和审批绑定Audit Event 与 Evidence 索引
多运行时共享 SkillSkill 不绑定 Claude；Codex、OpenCode、Kimi、WorkBuddy ACP 等适配器共享同一任务契约.devin/skills + Adapter mapping

新增约束：并行不是默认目标，可靠性才是。每个并行分支必须有独立工作区、预算和验证；如果运行时不支持并行，系统必须顺序降级并保留相同的状态和证据语义。
