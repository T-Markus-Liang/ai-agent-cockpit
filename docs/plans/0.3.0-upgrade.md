## 1. 版本目标

在保留微信身份、原生 Agent 历史和现有任务控制面的前提下，验证并接入 Pi Durable，形成“持续对话 + 后台执行 + 独立验收 + 可靠通知”的运行链路。人类确认方向、范围和预算，之后抽查；只有范围变化、权限失效或无法判定的高风险结果才再次请求决定。

本版首要成果不是更多 Agent 名称，也不是整体更换前端，而是任务不会因为手机断线、前台等待结束或运行服务重启而失去追踪。恢复不等于把旧指令再发送一次。

### 本版必须完成

- 修复并验证现有记忆提炼丢失昵称等关键事实的问题。
- 增加与供应商无关的 `RuntimePort`，迁移期提供 legacy 与 Pi Durable 两个适配器；同一请求只有一个 owner，完成迁移后退役重复活跃实现。
- 把交互等待期限与执行期限分开，显式后台任务独立于主对话取消。
- 保留可靠收件、正文冲突检测、持久补发和稳定请求标识。
- 保留原范围授权、硬约束、固定验收、独立 Reviewer 和完成凭据。
- 至少验证两个本机 CLI/ACP Worker 的受控调度；旧会话使用合成会话先验收。
- 仪表盘显示执行、恢复、待核对、验收和通知投递状态。
- 完成隔离故障注入、用户参与的真实微信抽验、迁移及回退演练。
- 按 [C01–C15 裁剪清单](0.3.0-pruning.md)删除重复调度、偏离设计的产品旁枝和独占依赖；隐藏菜单不算完成。

### 明确不纳入本版承诺

- 不承诺任意 GUI App 无人值守接管，Devin/WorkBuddy 等未验证能力继续显示待验证。
- 不批量导入或修改 Codex、Claude Code、Kimi 等原生数据库和 rollout。
- 不承诺外部副作用 exactly-once、通知已读或断电绝对零丢失。
- 不实现通用原始音频 ASR与二进制附件持久补发；语音仍依赖服务器转写。
- 不把 Pi Pocket 的 `/until` 或模型一句“完成了”作为产品任务完成门槛。
- 不改变当前主模型选择、人格文件、全局 Agent 配置或凭据存储方式。

## 4. 目标架构与唯一状态源

```text
微信 / Cezar / 可选手机 PWA
               ↓
入口鉴权、可靠收件、payloadDigest、路由绑定
               ↓
产品控制面：Task / Execution / SessionRef / Grant / Approval / Evidence
               ↓
RuntimePort（版本化接口；同一请求只绑定一个引擎）
       ├─ legacy：迁移期限定旧待办，验收后退役重复驱动
       └─ pi-durable：主对话、后台任务、运行事件与上下文压缩
               ↓
执行适配器：受控文件副本 / Native ACP / Cezar / 以后再接 GUI
               ↓
真实 Verification + 独立 Reviewer + Completion Proof
               ↓
现有持久 Outbox → 微信/界面通知
```

| 状态 | 唯一所有者 | 不允许的误判 |
| --- | --- | --- |
| 用户原始收件、游标、正文摘要 | 入口 MessageInbox | Pi requestId 去重不验证变更正文，入口不能删掉冲突检查 |
| 产品目标、授权、最终 Task/Execution 状态 | 现有产品控制面 | Pi 内部 Task completed 不代表产品完成 |
| Pi 对话、模型/工具任务、运行检查点 | 单进程 Pi Runtime | 不能让 Pocket 和 runtime 各开一个 Harness 拥有同一数据库 |
| 原生旧会话与认证 | 原生 Agent | Provider API 会话不代表 Claude Code/Codex App 原生会话 |
| 用户事实与原文归档 | 现有 Memory Service / Archive | 自动压缩不是事实提炼正确的证据 |
| 通知文本、发送尝试与外部 clientId | 现有 ReplyOutbox | 队列提交、接口接受、用户已读是不同状态 |

legacy 不是永久第二套运行底座。P6 灰度和回退通过后，P6c 删除新产品中重复的旧调度/缓存驱动。0.2.2 发布工件封存用于回退，不能与新 owner 同时拥有同一请求。Native ACP Worker 所需串行和原生历史锁不在删除范围。

### ID 映射

映射表持久记录 `userId/ownerId → sourceRequestId + payloadDigest → runtimeBinding + submissionId → productTaskId → executionId → durableTaskId/nativeRunRef → outboxDeliveryId`。会话另存 `RuntimeConversationId` 与原生 `SessionRef`，禁止互相冒充。

`runtimeBinding` 创建后不可随每条重试任意切换。代码版本、接口版本、授权摘要、执行工作目录及模型/provider 标识进入审计；URL/key 只使用本机私有引用，不进入映射、提示或日志。

## 5. RuntimePort 与执行边界

拟议接口：`submit(request)`、`wait(submissionId, waitContext)`、`observe(conversationId, cursor)`、`recover(ownerLease)`、`abort(target, scope)`、`inspect()`、`usage()`。提交入参包括 owner、请求摘要、授权引用、产品 ID 与明确上下文；返回持久 Submission ID，不持有 HTTP/微信连接。

取消区分四种：等待结束、当前交互轮停止、单个后台 Execution 停止、整个目标连后台停止。界面和微信命令必须明确范围；普通断线/等待超时不变成全局取消。后台任务实际期限由已批准的 Goal/Execution 决定，不能因新运行层自动延长授权。

Pi 的安全重放由工具实现者声明，不依赖模型概率：

- 只读查询、已验证幂等提交可以声明 safe，并使用持久 effect key。
- Native Agent 启动、shell、文件写入、外部消息默认 unsafe。
- 幂等启动必须先存产品 Execution 和 intent，再按 effect key 启动或查询；“启动了但未记下 runRef”进入核对，不重派。
- 新进程恢复时先建权限和模型注册表、恢复映射及预算，再恢复任务；缺定义、迁移失败和配置漂移等待处理。
- 模型/provider 重试不能提高预算；鉴权失败需要认证处理，不反复换模型或新建对话来绕过。

Chief 默认只有控制面查询、规划与受授权派单工具，不给裸 `CodingTools` 的宿主 bash/write 权限。Worker 的读写由文件 broker 和受控执行环境复核 exact paths、symlink、租约、grant 与 digest；`NodeExecutionEnv({cwd})` 本身不是沙箱。Reviewer 使用独立身份、只读环境和同一 artifactRef，不能改验收文件。

Jev 只可做路由/风险 advisory，不批准动作，不证明目标完成。权限、范围、算术预算与证据关系使用确定性规则。

## 6. 记忆与模型兼容

发布前先处理记忆缺口：事实保留 source event、原文引用位置、提炼版本和完整性状态。缺失客体的“用户希望被称为”不能标记 accepted；保留原文、有限重新提炼、最后进入 needs-review，不凭助手推测填名字。

测试至少涵盖中文昵称、姓名/数值、否定、更正、同名用户、冲突、忘记和删除策略。长期事实只来自用户表述；不能保证脱敏覆盖所有秘密，应减少送入模型的原文范围。

新的 Pi 对话由 Pi compaction 管 active transcript；现有 archive 和 Mem0 保持。统一 ContextAssembler 只注入一份人格、近期上下文/压缩和带来源的事实，不把 legacy summary 与 Pi summary 反复叠加。fallback、主/子会话使用稳定用户记忆命名空间，但工具内部状态不跨原生引擎伪装复制。

主对话继续选择用户当前的 Kimi。P0 先验证 Pi-AI 与现有本机 provider/shim 的模型 ID、流式行为、思考参数、工具和认证兼容；未验证不把模型 API 替换说成 Kimi CLI 会话恢复。凭据解析不得修改全局 `~/.pi`、`~/.codex`、`~/.kimi-code` 等配置。

## 7. 外部 Agent、前端与移动入口

通讯入口与执行Worker分开：微信是首个已运行适配器，后续平台不复制Chief/记忆/调度器，只接共同身份、Inbox/Outbox与RuntimePort。官方SDK可降低收发开发成本，但应用/租户认证、消息政策、回调防伪与媒体能力必须逐平台验；统一ChannelPort模板尚未编码。飞书/Lark优先候选、WhatsApp先确认官方账号与webhook条件，详细列表及T11见[通讯兼容表](channel-compatibility.md)。本轮没有登记新应用、读取新平台key、开公网地址或发送外部消息。

本版优先在批准的合成会话上验证 Codex/OpenCode 等至少两个 CLI/ACP adapter：发现、认证、真实 prompt、暂停/取消、准确恢复、冲突、超时、证据回传均须分别记录。Kimi 的既有前台兼容入口保持可用。WorkBuddy、Devin、Claude Code、Antigravity、DeepSeek Harness App 仅提升已经实测的能力，不把入口存在改成已连接。

用户旧会话需要明确选定 source、profile/account、nativeSessionId 和 cwd。先元数据、再必要片段；默认只读原库。不让新 Runtime 为恢复失败偷偷创建替代原生会话。

Cezar 当前中文入口保留。新增分离视图：用户 Task、产品 Execution、Pi 内部 Task 图、恢复原因/下一检查时间、待核对及通知状态。显示旧会话来源、真实能力与关联 Evidence，不再用一个绿色“完成”混合所有状态。

默认导航收敛为仪表盘、对话/任务、运行与验收、Agent/原生会话、设计工作流、日志/通知和设置。裁掉宣传入口、非必要远程遥测、旁路 issue/tracker/variant 页面与第二套流程执行器；核心 Git diff/worktree/review、设计工作流图、中文与可访问性保留。详见 [裁剪决定与保留底线](0.3.0-pruning.md)。

Pi Pocket 是可选移动试验，不是本版核心发布前提。独立试用只用合成任务与独立数据目录。生产接入必须通过单所有者 RuntimePort/RPC，改造其硬绑定 `PocketApp`，而不是直接共享数据库；若改造成本过高，先在 Cezar 增加响应式只读视图。新 UI 默认中文、高风险需产品审批，守住同用户跨设备认证与令牌撤销；不自动暴露公网 quick tunnel。

根据用户追加的 [Paseo 源码调查](../research/paseo-2026-10-07.md)，优先验证复用其原生 CLI 适配、旧会话和手机客户端，避免再造整套移动产品。Paseo 的 idle、heartbeat 和 provider goal 不替代产品 Completion Proof。若采用，Pi 只处理 Chief 持久运行，Paseo 处理原生 Worker；同一任务不能同时注册两套 schedule。现有微信/控制面/Mem0/Outbox 保留，Hub 不作为默认部署前提。

## 8. 数据迁移、灰度与回退

采用 `legacy → synthetic shadow → allowlisted canary → new submissions`。Shadow 默认只重放数据投影/假模型，不调用真实工具、模型或发送微信，不产生第二份实际执行。

| 0.2.2 数据类别 | 迁移决定 |
| --- | --- |
| received / queued 且确认未派发 | 清单、正文摘要与目标绑定校验后，可进入新运行层一次 |
| preparing 但旧进程仍活跃 | 等清理证据；不同时启动新引擎 |
| running / dispatched / tool_activity / uncertain | 留在原引擎核对或 drain；不能作为新用户输入重放 |
| result_ready / reply_pending | 仅移交通知映射，保留正文与 clientId，不运行 Agent |
| cancelled / failed / done | 作为只读历史/状态；不自动复活 |
| 原生 Agent 会话、登录和凭据 | 不迁移、不覆盖、不复制进新 Harness |
| 旧 Goal grant | 不扩大权限；需显式版本适配或新的范围确认 |

迁移使用可重复 dry-run 的版本化 converter、manifest、唯一映射和差异校验。完整归档按副本导入，保留 timestamps/来源，不给导入的旧消息创建 GenerationTask。数据库备份使用停写快照或 SQLite backup，包括一致的 WAL 状态，不能只复制正在写的主数据库文件。

回退先冻结路由和新真实执行，再按 owner/fencing token 确认租约唯一。已有新引擎任务继续 drain 或保持待核对，不重新塞给 legacy。回退仅改变未来提交的默认绑定；新数据和所有未送达文本保留。旧二进制不打开新版 Pi 数据库，禁止把旧备份覆盖新数据。

## 9. 发布门槛

- G0：基线/依赖/授权/数据清单明确，记忆失败案例可复现。
- G1：记忆完整性与主 Kimi provider 兼容 canary 通过。
- G2：RuntimePort contract、持久化、重放和取消语义通过隔离测试。
- G3：微信入口、任务关联与持久 Outbox 联合测试通过；真实回包由用户抽验。
- G4：至少两个本机 Worker 的合成调度通过，验收/独立复核与权限负例不退化。
- G5：干运行、备份、单所有者切换及回退演练通过。
- G5c：强制 P6c 裁剪完成，V46–V52 通过；重复驱动已退役，删除/隔离/不新建清单可审计。
- G6：G5c 通过后，新版本连续 24 小时观察、合盖/电池/网络测试与公开发布检查通过。
