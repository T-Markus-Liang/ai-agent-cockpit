## 3. 一批实现、一份交接、一次针对性审计

执行方不用每写一个函数就停。将一个可核对的小里程碑打包，自测后交接；审计与实现可以错位并行，但只在不冲突的文件/独立工作包内继续。

```text
执行AI按现行计划实现 + 自测修复
  → 冻结该批版本 + 写交接包，标READY_FOR_REVIEW
  → 本线程核对引用/范围 + 读diff + 核验/隔离复现
  → 审计报告：接受限定组件 / 缺证据 / 需修改 / 暂不能审
  → 执行AI按Finding ID修复并交新revision
  → 本线程复核，更新计划/门槛和下一批优先级
```

默认共享文件接力，不依赖你复制全部聊天记录：

- 执行方写`docs/handoffs/<batch-id>-r<n>.md`，格式用[执行交接模板](../collaboration/execution-handoff-template.md)。每个revision单独文件，旧证据不覆盖。
- 本线程写`docs/audits/<batch-id>-r<n>.md`，格式用[审计结果模板](../collaboration/audit-result-template.md)。不通过聊天里一句“完成了”判断已交付。
- 执行方首次填写真实App/线程或agent reference、工作目录/branch、可写文件，并确认已读本协议；身份不按会话标题猜测。
- 对方交接后，你在这里说“审计最新交接批次”即可，我读共享材料；有明确批次可直接指定ID。
- 本轮未创建定时监听/新的监督Goal，未向外部App自动发消息。持续自动监督需要另行明确启用；无法核实live handle时不声称对方仍在运行。

可以把这一段一次性发给执行同事：

```text
你负责0.3.0功能实现、自测和返工；另一个线程负责审计与优化方案/执行计划。
请读 docs/plans/0.3.0-collaboration.md，先确认你的App/线程/branch和可写文件范围。
按现行Goal Prompt和检查点推进；每完成一个可核对批次，按 docs/collaboration/execution-handoff-template.md 写 docs/handoffs/<batch-id>-r<n>.md。
记录精确代码版本/未提交文件hash、测试命令与退出码、覆盖/未覆盖事项、真实副作用与活动handle，标READY_FOR_REVIEW。
不要把自测当独立审计/上线，不改审计报告或降低固定验收；按审计Finding ID修复并交新revision。等待审计时可继续不冲突、范围已准的独立工作，不擅自部署。
```

## 4. 审计必须绑定版本，而不是只看当前HEAD

优先交接一个明确commit/PR与base commit；不能为了交接把别人dirty修改一并提交。未提交工作用“批次变更文件清单 + 每个文件SHA256 + base HEAD + 新建/修改/删除/rename列表 + 依赖lock/实际运行工件”作为sourceRef，公开清单不含私有状态/认证/用户原文。

执行方声明该批次的变更文件、直接接口依赖和测试配置已冻结；其他独立文件仍可修改。若使用worktree/副本，必须包含当前未提交/未跟踪改动和依赖，不可仅克隆HEAD导致漏审。不要测试活跃生产DB/共享向量库。

审计前后重新核对变更及相关依赖的hash。发生漂移，结论只属于旧sourceRef，新revision必须重审；测试期间来源漂移也不能拿那次结果给新代码背书。正在写的WIP可做建议性阅读，但不能签正式接受。

“代码身份正确”是确定性校验，不调用Jev；Jev只可提醒自然语言报告可能越过证据范围，不能代替diff、测试或授权。

## 5. 四类结论与失败返工

| 结论 | 含义 | 下一动作 |
| --- | --- | --- |
| COMPONENT_ACCEPTED | 指定sourceRef在指定组件范围通过；列明证据、限制和是否独立 | 执行方继续依赖已满足的下一批；生产状态仍单列 |
| CHANGES_REQUESTED | 有可定位的缺陷/违反固定要求，标Finding ID和严重度 | 执行方返工、补负例，交新revision；本线程不代修 |
| EVIDENCE_REQUIRED | 代码可能已有，但关键测试/真实路径/版本绑定不足 | 补所列证据，不当作完成；不能“换个说法”消掉失败 |
| WIP / NOT_REVIEWABLE | 代码在变、交接缺失、来源无法固定或未在可审核范围 | 保留观察/建议，要求冻结批次；不冒称失败或通过 |

Finding ID稳定，例如`M01-F001`；修复包逐条回答已修、理由拒绝或待决，引用新diff/负例。历史失败与不明结果保留，不覆盖日志、重置状态或换新request ID绕过。审计方若修了功能代码，便不是该修改的独立Reviewer，需要第三位未参与实现者；目前本线程不这样做。

## 6. 避免审计变成新的吞吐瓶颈

| 风险边界（代码定义，不是模型授权） | 协作规则 |
| --- | --- |
| 已准范围内文档/纯展示等低风险变更 | 执行方自测后交批次，审计可批量抽验；不得跳过中文/可访问性或夹带权限变更 |
| 普通源码与接口实现 | 自测后进入审计；可先推进无依赖、无文件冲突的下一任务，不必等每个函数获准 |
| 记忆/身份/权限、数据迁移、恢复/幂等、fallback/预算等核心风险 | 全量针对性审计、故障负例和守恒证据；未关闭阻断项不得让依赖链过门槛 |
| 生产切换/旧历史写入/外发/公网/物理裁剪/发布 | 原用户授权与产品Gate先核对，必要时请求具体确认；文档审计绿灯不等于动作被批准 |

必须修复与改进建议分开：安全/数据守恒/固定验收缺陷阻断对应门槛；非阻断改善进backlog，不让实现长期排队等措辞润色。风险不确定就按高风险边界收敛，但继续其他安全独立项，不冻结整项目。

文档若改动授权、预算、固定验收、迁移或发布条件，按实际风险处理，不因文件后缀为.md自动降为低风险；“仅文档”不能绕过范围变更确认。

## 8. 方案/执行计划如何迭代

审计方以发现的事实提出“当前缺口→对原要求的影响→最小修正方案→依赖/测试/回退→执行方下一动作”，维护计划revision和决策记录。固定验收、预算、权限或核心范围的变化必须显式标明并由有权者决定，不通过删case/换目标取得更容易的绿灯。

状态账本分列实现、自测、独立审计、部署/真机；具体sourceRef和日期不可缺。本线程只对自己审过的范围署名，对自己先前编写的预检/selector等组件不能自签独立审计；执行方若大改这些组件，重新说明作者与审查独立性。

实施顺序：先关闭M01的旧记忆升级与版本/守恒阻断，再补M02真实跨层接线；P0依赖/许可/遥测审计可与不冲突的P1/P2工作交错进行。不是因为当前容易测的组件过了就缩小整个0.3.0目标。

## 9. 本轮Jev使用边界

按typesafe-ai读取官方索引及Noul/置信度说明，使用本机jev-eval检查两组**合成交付措辞**：把“仅组件合成测试”说成“全部已上线24h稳定”得到越界概率0.98/0.96；明确“组件测试通过、生产/耐久待验”得到0.06/0.20。第二组输入尝试带criteria.true/false，但后续核对wrapper会丢弃Noul.criteria，不能宣称它实际生效；后两轮均把边界写入instructions。模型jev-1.13.0；措辞变化造成概率差异，更不能用分数直接批准审计。仅作风险advisory，不含密钥、真实原文或同事私有聊天。

Noul没有单独confidence。工程判断、hash/规则/预算校验和高风险授权不交Jev；概率不作为通过门槛。依据：[官方Noul](https://docs.typesafe.ai/primitives/noul)、[置信度](https://docs.typesafe.ai/confidence)。
