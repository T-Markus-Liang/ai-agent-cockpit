## 1. 版本目标与取舍

让现有可靠执行控制面成为用户容易理解的“队友工作台”：微信交代目标、多个明确角色协作、后台工作有进度、结果经过验收、记忆可查看和更正，移动端能找到连接、审批和运行历史。

不追求 Grok Bot 像素级复刻。**不直接替换成 Codync/OpenMausBot/Rakazo，不新增它们的 daemon/数据库与我们的 runtime 双活。** 采用接口、交互和测试模式，在现有薄适配层落地；确需使用上游 host 时先做独立 spike，证明单 owner/数据边界后再裁决。

优先级按依赖确定，不按 Stars：

1. 明确 Bot/Profile、原生 Agent、会话线程、Task/Execution 的映射。
2. 改善任务/对话可视化与统一事件投影。
3. 同一 runtime 下的 Routine 和有界团队协作。
4. 记忆/上下文可视化，再扩设备和外部算力。

原生 iOS、群聊自动协作、远程桌面、商业多租户、更多通讯平台均为条件项，不默认塞进首批。继续使用 Kimi 主对话及当前人格；bot 角色不自动获得工具权限。

## 2. 目标结构：保留唯一执行权威

```text
微信 / 中文 Web（移动适配）/ 后续 Channel
  → 同一 identity + Inbox/Outbox + Approval
  → Bot/Profile 与 Thread 的产品读模型
  → 既有 Task / Execution / Attempt / Grant / Effect / Evidence
  → 唯一 RuntimePort / ownership / route / SessionRef
  → native CLI、已准云 Worker（按 scope）
  → 固定验证 + 独立 Reviewer → Completion Proof → 可靠回报
```

上游名词只是映射参考：

| 上游概念 | 我们的承接 | 禁止误用 |
| --- | --- | --- |
| Bot | Agent/Profile 的持久角色与 UI 投影 | 新建另一个 Chief 和私有任务账本 |
| Thread | 产品对话分支 + 明确 SessionRef/ownership | 按标题猜旧会话；静默替代 Native Session |
| Run | 既有 Execution 与运行状态 | 新建第二套 Run ID/DB 同时决定执行 |
| Attempt | 既有 Execution.attempt / runtime attempt 证据 | 为逃避不明效果重新造 Task |
| Routine | 已授权 Goal 的 trigger definition / occurrence | 无限 cron 发送“继续”替代持久 Goal |
| Lease/fence | worker ownership/并发和提交守卫 | Lease 续期等同用户 Grant 续期 |
| Result/push | 既有 Outbox/投递证据 | “模型返回”或“已发送”直接标 Task 完成 |

所有新 schema 名称/版本以实施时实际接口为准；本表不表示新对象已经存在。对既有字段用显式 converter/DTO，不做全局 rename。

## 3. 候选工作包与验收

### N01 — Bot 工作台与可验证 Agent 能力

参考 Codync 的可联系角色、Maus 的 instance/driver/model 分离。沿用现有前端和路由，先增加统一 Bot/Profile 读模型；呈现账号/后端/模型/工作目录/会话/真实能力证据和连接状态。

区分 discovered、authenticated、prompt-verified、resume-verified、unavailable；时间戳和测试 scope 可查看。自定义名字/人格不改变角色授权。配置更新有版本/摘要，影响在飞任务时不静默重启/换模型。

验收：同一个 agent 两账号/两个 profile 隔离；“可执行文件存在”不变成 authenticated；不可用实例仍显示具体原因；当前主助理模型不被界面默认值覆盖。

### N02 — 对话与执行分层、统一事件投影

参考 Codync id/rev catch-up、Maus 规范化事件/原生 inspector。扩现有日志和详情页，UI 始终显示“正在聊天”“后台执行”“待审批/核对”“执行返回待验收”“投递待补发”，不让同一段聊天冒充多个状态。

引入版本化只读事件 DTO：eventId、sequence/cursor、entityId、attempt/owner、状态引用、脱敏摘要。业务状态和效果意图先可靠持久化；文本 delta 可短窗口合并，但不得影响审核与恢复。原生协议详情单独授权，不公开用户原文/秘密。

验收：断网、半开连接看似 connected 但无消息、重连、乱序、重复、漏 sequence、慢客户端可追赶；用可见 heartbeat/有界 stale 检查识别连接失活，游标只在成功消费/快照后推进；投影从事实重建；磁盘失败标不完整，不能基于 live event 签完成；没有第二个可写状态源。

### N03 — Routine：持续目标的可靠触发，不另造 scheduler

参考 Codync occurrence/run/独立结果发布。先支持一次性、interval、cron + IANA timezone；webhook/第三方订阅另批。定义包含目标、条件、验收、scope、Grant 引用、预算/期限、通知策略、missed/overlap policy。

触发进入现有 Goal/Runtime 单一 admission；以 routineId + occurrenceId 防重，而不是通用聊天收到定时“继续”。长期 Goal 的内部检查点由既有 runtime 推进，routine 仅负责新 occurrence 的准入。每次 occurrence 的执行预算、父预算与用户授权同时生效，不能每次唤醒重新发一份更大预算。

默认错过 interval 合并，只保留一个待检查；重叠先 defer/coalesce，明确可选 skip。paused/deleted 停止未来准入，不偷偷杀已经获准的在飞执行。未知 prompt/effect 不自动重放；结果已生成只补发。

验收：DST、时区编辑、合盖/wake、并发 tick、错过 100 次只产生政策允许的一次、停用/删除、已过 Grant、在飞取消、存结果后崩溃、发送后未 ack。创建 routine 不自动做真实 test run。

### N04 — 有界团队协作与独立 Reviewer

参考 Codync wait graph/quota 和 Maus room goal 的独立生命周期。复用 Chief MCP/Task/Execution，提供明确 ask/delegate/status/cancel 合同，而非模型自由互喊。

每次派单携带 parent task/execution、准确 recipient、同 artifact 引用、参数 digest、已准 scope、期限、预算、回复形式；在同一 ownership 图核对 cycle、hop、排队容量与取消。hop/quota 的具体值按本项目预算确定，不照搬上游常数。

Reviewer 是独立 execution/身份，读同冻结工件与固定验收，OS 只读；不得自改验收、不将中间 bot 的 turn.completed 当团队目标完成。最终结算仍由 Completion Proof。需要实质独立时，不以同一实现者换显示名冒充 Reviewer。

验收：循环等待、同 body 幂等/异 body 冲突、父取消传播、非目标执行不受影响、超时 recipient、队列饥饿、审批漂移、Reviewer 写工件被 OS 拒、Worker 声称完成但检查失败仍未完成。

### N05 — 可见、可编辑、有来源的记忆与上下文

参考 Maus memory gauge/hash 编辑/撤销、Rakazo revision、Codync snapshot + compaction epoch。**Mem0/现有质量与隐私层仍是事实权威**；Markdown 可以作为导出/读投影，不能成为第二事实源。

UI 显示正在使用哪些事实、来源、可信/冲突状态、用户或 bot scope、预算裁剪及最后修订。更正/删除/撤销通过现有 reconcile/purge/epoch；Undo 不能复活 Forgotten/tombstone。编辑用 expected revision/hash；冲突呈现两版，不覆盖 bot 同时写入。

稳定 prompt snapshot 与易变内容分离。普通变更可按 revision 增量注入以节省缓存；隐私重置/授权失效必须立即拒旧上下文，不等 compaction 才生效。外呼仍按真实字段与目的 provider 控制，不把导出正文自动送远程模型。

验收：同修订重复注入、事实过期、跨用户/跨 bot、编辑竞争、摘要丢关键来源、forget 与生成/投递并发、模型 fallback 仍保留正确记忆和预算；日志/界面无秘密。

### N06 — 移动入口与审批发现性

先优化现有中文 Web 的移动布局/PWA 可行性，不同时重写三套客户端。仪表盘直接展示微信连接/二维码、Bot、持续 Goal、待审批、待核对、未送达和运行历史；核心入口不能藏在深层设置。

登录与微信绑定是不同身份动作；二维码和私有 token 不进共享日志/缓存。离线展示标最后同步时间；审批过期必须重新查权威，不从离线卡片直接执行。后续 native app 或 relay 单独 spike，设备配对可撤销，服务端数据最小化。

验收：手机浏览器实际页面、中文/语言切换、键盘/屏幕阅读器、断线状态、撤销设备、过期卡片、错账号、同意按钮防重复；未接平台如实显示未接入。

### N07 — 云算力适配（条件项）

按用户现行路由：CPU 异步任务用 Jules，GPU 用 Colab，大件用 Drive；本机只做编排/验收/合并/常驻。通过现有 dispatcher 增 resource descriptor 与私有 credential reference，不新建独立调度 Goal。

任务 Manifest 区分公开 repo 与私有数据，固定 sourceRef、允许路径/数据、预算/期限、job handle、输出摘要；Jules PR 不自动合并，Colab new→上传→运行→回传→stop，Drive 中转有留存/清理范围。未知外部 launch 先核对，不自动重复创建 session/VM。

接入前核验 wrapper：key 不得进入 argv、prompt、日志或 git。当前 jules run 实现有把 key 传给子进程参数的链路，且默认 AUTO_CREATE_PR；本轮未调用 run，这是一项接入前需整改的包装器风险，不是已观察到 key 泄漏。只读研究和实现派单模式要分开。

验收：过期/撤销拒派、源漂移、launch 成功但响应丢失、已有 handle 恢复、同结果归档去重、私有数据出站拒绝、PR 检查失败不合并、回传前异常不误报清理完成。

真正的 24h 要有常开的执行节点或已获准远程 Worker；不能宣称 Mac suspend 时仍在本机执行。云端 relay 只转发消息，不自动提供本机算力。

## 4. 分批执行顺序与裁剪

| 批次 | 前置与结果 | 退出条件 |
| --- | --- | --- |
| R0 合同映射 spike | 固定 0.3.0 基线；对三项目模式做接口/数据差异 | 一张映射表、一条合成链路；无第二可写 owner |

| R4 条件扩展 N06-native/N07 | 独立授权、资源/许可证/协议核验 | 真机或云路径证据、回退、明确能力表 |

不安装完整第三方产品作为隐藏后端；不把 UI 快捷派单复制成第二种执行入口。删除已有重复实现必须先有真实替代、drain 和回退，不能以“参考新项目”为由丢旧任务/会话/记忆。已退役组件不因复用上游重新引入。
