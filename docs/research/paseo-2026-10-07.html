能否让 Agent 一直自己推进

可以复用它的编排与续办能力，不必另写全部管道。

编排文档和续办工作流提供实际接口。 它支持周期检查、后续指令和跨供应商复核。 这符合“人类定方向、途中抽查”的使用方式。

仍有三个重要边界：

  • 心跳目标正在运行时，调度器拒绝叠加新运行。
  • daemon 重启把未结束的 schedule run 标为失败。
  • 恢复会话不证明 CLI 内部的后台 shell 或工具已恢复。

源码：schedule/service.ts:592–624、855–866。 正式版也保留相同的重启失败与忙碌拒绝逻辑。 心跳不会提供工具步骤级的安全重放证明。 机器真正休眠时，任何本机 daemon 都不能继续执行。

MessageReceipts.sendOnce 先写 pending 再派发。 已有 completed 回执不会重发，参数冲突会拒绝。 pending 在重启后属于未知结果，不代表已经安全失败。 这个设计可复用，但不能宣称 exactly-once。

对当前升级的建议

遵循 ponytail：复用现成入口，不再做整套第二手机产品。 先验证 Paseo 的 CLI 执行与手机端，不整仓复制。 保留现有控制面、微信、Mem0、授权、审计和完成门槛。

Pi Durable 仍是 Chief 持久运行的候选。 Paseo 管原生 Worker，Pi 不再重复管理同一 Worker。 每个任务只选一个 schedule owner。 Paseo、Pi、旧 Goal 调度器不能三方重复派单。 Hub 与 Pi Pocket 本版不作为默认必装项。

层 推荐职责 不应重复实现
现有产品控制面 微信 Kimi 助理、授权、记忆、验收、通知 不重写完整移动客户端
Paseo 候选 外部 CLI、原生会话、状态流、worktree、手机观察 不另建一套产品完成标准
Pi Durable 候选 Chief 的持久对话和运行检查点 不再驱动同一个原生 Worker

这只是采用建议，不是已经部署的架构。 它不能解决机器真正休眠时的本地执行问题。 全天执行仍要求运行宿主保持在线。

建议 P0 追加候选验证，P4 采用合成原生会话。 先验 Codex/OpenCode/Kimi，再判断可删哪些旧管道。 需要核对 SDK、手机端和 daemon 的准确版本。 新增能力检查 server feature，缺失时不静默降级。

隔离试验应使用独立 PASEO_HOME 和 loopback 端口。 关闭 relay、真实通知与自动安装/同步全局 skills。 不修改本机原生认证，不启动 GUI 接管。 试验失败仍使用 0.2.2，不让旧待办自动重派。
