结论：Paseo 值得优先验证为外部 Agent 执行层和手机入口。
它已有跨供应商派单、旧会话导入和心跳续办。
微信、共享记忆和产品验收仍需我们的控制面。
本次阅读源码与测试定义，没有运行 Paseo daemon 或接管旧对话。

它更像“外部 Agent 调度台”，不只是手机聊天壳。
但它还不是开箱即用的全机私人管家。
依照 ponytail 的最小复用原则，优先复用现成通道和手机端。
不因此新增第二套任务控制面。

原生会话导入不是简单复制聊天文本。
它使用 providerHandleId 和 cwd 恢复，再读取原生历史。
但来源、账户、profile 和占用冲突仍须精确核对。
本次没有读取或恢复 Markus 的真实旧会话。

语音不是只有录音按钮。
voice mode 会用独立 Agent 对话，通过 MCP 控制执行。
默认本地 STT 是英文 Parakeet v2。
可选 v3 的 25 种欧洲语言也不包括中文。

语音接口允许分开配置 OpenAI 兼容 STT/TTS 地址。
这给复用中文语音服务留了入口，但还须实测。
依据：[voice 文档](https://github.com/getpaseo/paseo/blob/8ddeb79c8dbb8934244b35ba18472fb9074d8209/public-docs/voice.md)。

## C 能否让 Agent 一直自己推进

可以复用它的编排与续办能力，不必另写全部管道。

```flow LR
主Agent -> 选择provider与profile
选择provider与profile -> 独立Worker与worktree
独立Worker与worktree -> 主Agent: 状态和结果
heartbeat -> 主Agent: 周期唤醒同一对话
主Agent --> 独立Reviewer: 可按工作流派单
```

[编排文档](https://github.com/getpaseo/paseo/blob/28f7528588bc4ea74d4b9394560191bc16c20b84/public-docs/orchestration.md)和[续办工作流](https://github.com/getpaseo/paseo/blob/28f7528588bc4ea74d4b9394560191bc16c20b84/public-docs/orchestration-workflows.md)提供实际接口。
它支持周期检查、后续指令和跨供应商复核。
这符合“人类定方向、途中抽查”的使用方式。

仍有三个重要边界：

- 心跳目标正在运行时，调度器拒绝叠加新运行。
- daemon 重启把未结束的 schedule run 标为失败。
- 恢复会话不证明 CLI 内部的后台 shell 或工具已恢复。

源码：`schedule/service.ts:592–624`、`855–866`。
正式版也保留相同的重启失败与忙碌拒绝逻辑。
心跳不会提供工具步骤级的安全重放证明。
机器真正休眠时，任何本机 daemon 都不能继续执行。

## D 必须保留我们的哪些底线

```callout warn Paseo 的 idle 不等于我们的任务已完成
SDK 的 idle 只表示一次 Agent 回合结束。
产品完成仍须真实测试、独立复核与完成凭据。
Codex auto-review 在这里处理工具审批，不是项目验收。
```

| 边界 | 核对结果 | 我们的处理 |
| --- | --- | --- |
| 重复提交 | 有持久 create/send 回执 | 持久映射产品 Task/Execution 与 Paseo agent/message ID |
| 派发结果不明 | 返回 `agent_request_outcome_unknown` | 保留待核对；不换新 messageId 强行重派 |
| 目录授权 | daemon 权限当前为整台 daemon 范围 | 保留 Grant/Approval、参数摘要与 OS 约束 |
| 本机数据持久化 | JSON 临时文件加 rename | 未见该 helper 做 fsync；不能保证掉电零丢失 |
| Agent/插件权限 | 使用宿主用户权限；插件能接触机器 | Chief 不直接获得无范围约束的调度或 shell 权限 |
| 手机配对 | 有可选 E2E relay、直接连接与凭据机制 | 配对链接不公开；隔离测试先关闭 relay |
| 语音与日志 | 中文资源不是中文 ASR；日志仍可能含原文 | 中文语音实测；私有日志与最小发送范围 |

源码：[消息回执](https://github.com/getpaseo/paseo/blob/28f7528588bc4ea74d4b9394560191bc16c20b84/packages/server/src/server/message-receipts/index.ts#L25)、[权限边界](https://github.com/getpaseo/paseo/blob/28f7528588bc4ea74d4b9394560191bc16c20b84/docs/permissions.md)、[原子文件写入](https://github.com/getpaseo/paseo/blob/28f7528588bc4ea74d4b9394560191bc16c20b84/packages/server/src/server/atomic-file.ts#L5)。

`MessageReceipts.sendOnce` 先写 pending 再派发。
已有 completed 回执不会重发，参数冲突会拒绝。
pending 在重启后属于未知结果，不代表已经安全失败。
这个设计可复用，但不能宣称 exactly-once。

手机端若直接派单，会绕过我们的产品审批入口。
初期应只观察运行，或通过受控入口提交。
源码的 daemon 权限还不能宣称按项目精确隔离。
relay 端到端加密也不替代模型服务的数据边界。

## E 所有 App 都能连吗，Hub 要不要上

| 对象 | 判断 |
| --- | --- |
| Codex / Claude Code / OpenCode CLI | 有直接适配、旧会话导入与恢复代码；本机仍需认证与实测 |
| Kimi CLI | 通过 ACP；正式版也有专门适配，旧会话和思考选项须按 CLI 版本验证 |
| Codex App | 可通过原生线程接口接触历史；不是操作 GUI，也不保证双写安全 |
| Antigravity | 主分支有 `agy` 插件；正式版 provider 文档未列出该内置集成 |
| WorkBuddy App | 未发现同名专门适配；Codebuddy Code 目录项不能等同于 GUI 会话接管 |
| Devin App | 未发现专门 GUI 适配；通用 ACP 源码提及 Devin CLI 参数兼容 |
| DeepSeek Harness App | 未发现专门适配；要看本机 App 是否提供可验证的 CLI/协议入口 |

Antigravity 主分支目前只支持 full access。
它使用 `--dangerously-skip-permissions`。
重启后 `agy` 保留对话，但不重放历史到 Paseo 界面。
这不能直接进入我们默认的无人值守执行白名单。
详见[该 provider 的限制](https://github.com/getpaseo/paseo/blob/28f7528588bc4ea74d4b9394560191bc16c20b84/public-docs/supported-providers.md#antigravity)。

Hub 是独立开源仓库，也可自托管。
它提供事件接入、工作流和审计，不只有远程桌面。
支持 GitHub、Linear、Slack、Discord 和手动触发。
本次只核对其 README、许可证和 Paseo 侧契约。
没有全面审查 Hub 源码或运行测试。

[Hub README](https://github.com/getpaseo/hub)明确警告早期开发和数据丢失风险。
不把它立即替换为唯一生产控制面。
现有微信链路也不会因安装 Hub 自动获得连接。

## F 对当前升级的建议

遵循 ponytail：复用现成入口，不再做整套第二手机产品。
先验证 Paseo 的 CLI 执行与手机端，不整仓复制。
保留现有控制面、微信、Mem0、授权、审计和完成门槛。

```flow TB
微信文字与转写语音 -> Kimi助理与产品控制面
产品控制面 -> 范围授权与Task与Execution
范围授权与Task与Execution -> 薄Paseo适配器: 验证通过后采用
薄Paseo适配器 -> 外部原生CLI与旧会话
外部原生CLI与旧会话 -> 测试与独立复核
测试与独立复核 -> 持久Outbox与手机抽查
Paseo手机端 --> 外部原生CLI与旧会话: 同一daemon观察
```

Pi Durable 仍是 Chief 持久运行的候选。
Paseo 管原生 Worker，Pi 不再重复管理同一 Worker。
每个任务只选一个 schedule owner。
Paseo、Pi、旧 Goal 调度器不能三方重复派单。
Hub 与 Pi Pocket 本版不作为默认必装项。

| 层 | 推荐职责 | 不应重复实现 |
| --- | --- | --- |
| 现有产品控制面 | 微信 Kimi 助理、授权、记忆、验收、通知 | 不重写完整移动客户端 |
| Paseo 候选 | 外部 CLI、原生会话、状态流、worktree、手机观察 | 不另建一套产品完成标准 |
| Pi Durable 候选 | Chief 的持久对话和运行检查点 | 不再驱动同一个原生 Worker |

这只是采用建议，不是已经部署的架构。
它不能解决机器真正休眠时的本地执行问题。
全天执行仍要求运行宿主保持在线。

建议 P0 追加候选验证，P4 采用合成原生会话。
先验 Codex/OpenCode/Kimi，再判断可删哪些旧管道。
需要核对 SDK、手机端和 daemon 的准确版本。
新增能力检查 server feature，缺失时不静默降级。

隔离试验应使用独立 PASEO_HOME 和 loopback 端口。
关闭 relay、真实通知与自动安装/同步全局 skills。
不修改本机原生认证，不启动 GUI 接管。
试验失败仍使用 0.2.2，不让旧待办自动重派。

## H 今天的新修复为什么与我们有关

补读提交：[8ddeb79c](https://github.com/getpaseo/paseo/commit/8ddeb79c8dbb8934244b35ba18472fb9074d8209)。
它修复了 Claude 后台小弟与主对话的状态混淆。
这直接关系到“后台继续干，手机仍能正常聊天”。

| 问题 | 补读源码中的处理 |
| --- | --- |
| 小弟后台工作，主对话却一直显示 running | 用 Claude 自己的主回合事件判定，避免按帧形状猜测 |
| 用户发消息或按 Stop，误杀后台小弟 | 声明 `perTaskStopAffordance`，区分主回合与后台任务 |
| 出生就在后台的小弟，被误记为 canceled | 同时读取 `task_started.is_backgrounded` 与后续状态 |
| 队列放行消息，撞上后台完成后的唤醒 | App 队列使用 `steer`，合入支持该能力的当前回合 |

依据：[Claude adapter](https://github.com/getpaseo/paseo/blob/8ddeb79c8dbb8934244b35ba18472fb9074d8209/packages/server/src/server/agent/providers/claude/agent.ts#L3406)、[App 队列](https://github.com/getpaseo/paseo/blob/8ddeb79c8dbb8934244b35ba18472fb9074d8209/packages/app/src/runtime/host-runtime.ts#L2429)、[生命周期说明](https://github.com/getpaseo/paseo/blob/8ddeb79c8dbb8934244b35ba18472fb9074d8209/docs/agent-lifecycle.md#L200)。

对应真实 Claude 测试定义覆盖消息、Stop 和嵌套后台任务。
本机没有运行这些测试，不宣称其全部通过。
这批修复在 beta 主分支，不在正式版 0.10.3。

```callout warn 三种结束状态必须分开
主回合 idle，不代表后台小弟已经结束。
后台小弟结束，也不代表用户目标已通过验收。
重启后能恢复对话，更不证明工具副作用可安全重放。
```
