语音丢失 bug 已修复并部署。新消息先保存完整转写，再排队处理。真实 Kimi 隔离验证通过；实际微信回包仍需新发一条语音抽验。

## A 为什么后面的语音没反应

前一轮处理达到 5 分钟上限。旧代码随后清空队列，丢弃后发的语音。超时提示又被旧会话过滤器拦截，用户看不到失败原因。

日志显示 09:02 和 09:17 收到的后续语音只进入队列。旧版本没有保存完整收件，不能从截断的日志预览恢复。请重发这些旧语音。

## B 现在如何保留消息

```flow TB
微信语音 -> 私有收件箱: 完整服务器转写和元数据
私有收件箱 -> 提交轮询游标: 写盘成功后
私有收件箱 -> 按顺序排队
按顺序排队 -> Agent处理
Agent处理 -> {是否超时?}
是否超时? -> 对话结束回执: 否
是否超时? -> 未完成提示: 是
未完成提示 -> 保留后续队列
保留后续队列 -> {进程清理确认?}
进程清理确认? -> 按顺序排队: 是
进程清理确认? -> 等待核对: 否
```

- 语音先回复“转成文字并保存”，长处理给进度提示。
- 清理期间的新收件也保留，不抢到旧消息前面。
- 重启只恢复未开始的消息；执行结果不确定的不重放。
- 微信发送 `/消息` 查看最近 5 条状态。
- 没有转写或转写为空白时明确提示重发。

## D 已知边界

```callout warn 这些能力尚未完成
依赖微信返回的语音转写，未接入原始音频 ASR。前台仍有 5 分钟上限，任意长任务尚未独立转到后台。本轮未做 24 小时合盖耐久验证。
```

仅在未观测到输出或工具活动，且旧进程已清理时，允许一次 fallback 重试。未报告的副作用仍有重复风险，不保证 exactly-once。Jev 的脱敏风险提示仅作参考。

`done` 表示对话轮次结束，不证明控制面任务验收通过，也不保证微信对端收到消息。普通进程退出的未开始消息会保存在磁盘，但不是所有异常都能即时恢复。

新收件位于微信实例的私有 `incoming-receipts/`。文件为 0600，不提交公开 Git。回退前先停桥并备份；不要删除收件或批量重放不确定的请求。

重新验证：先运行 `npm --prefix vendor/wechat-acp run build`，再运行 `npm --prefix vendor/wechat-acp test` 和 `npm run test:voice-live`。最后新发一条微信语音，检查确认、回复和 `/消息` 状态。
